# 2026-07-23 — Session record

**Environment confirmed today:** WSL2 Ubuntu 24.04 (Noble), native Docker
Engine, NVIDIA GeForce RTX 4070 SUPER (laptop, dual-GPU alongside an
Intel UHD 770).

## Up

- **Gazebo GUI rendering at all.** Fixed a black-screen issue by
  switching `PX4_GZ_WORLD` from `baylands` to `default`. `baylands`
  likely hangs fetching remote terrain/textures from Gazebo's Fuel
  asset servers on first load; `default` is fully local and starts
  clean.
- **GPU-accelerated rendering, end to end.** Confirmed via:
  ```
  glxinfo | grep "OpenGL renderer"
  → OpenGL renderer string: D3D12 (NVIDIA GeForce RTX 4070 SUPER)
  ```
  Got there by, in order:
  1. Installing the NVIDIA Container Toolkit on the WSL2 host and
     adding a `deploy.resources.reservations` GPU block to compose —
     this alone got `nvidia-smi` working inside the container (CUDA
     path), but did **not** fix OpenGL.
  2. Mounting `/usr/lib/wsl` + `LD_LIBRARY_PATH=/usr/lib/wsl/lib` to
     expose WSL's Mesa/D3D12 library stack to the container.
  3. Mounting the `/dev/dxg` device — the actual GPU device node; the
     library mount alone gives the container the code to speak D3D12
     but nothing to talk to.
  4. `GALLIUM_DRIVER=d3d12` — without this, Mesa silently defaults to
     `llvmpipe` even with the libraries and device present.
  5. `MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA` — without this, on this
     dual-GPU laptop, WSLg picked the integrated Intel GPU instead
     (`D3D12 (Intel(R) UHD Graphics 770)`). This was the last piece
     and confirmed the fix.
- **Console control confirmed working.** `docker attach agere-px4-sitl`
  → `pxh>` shell → `commander arm -f` → `commander takeoff` flies the
  drone in the running Gazebo instance. Added `stdin_open: true` /
  `tty: true` to the `px4-sitl-gazebo` service to make `docker attach`
  usable for this.
- **Stack simplified.** Decided to strip `docker-compose.yml` down to
  just `px4-sitl-gazebo` — removed `dds-agent` and `ros2-bridge` — to
  isolate GPU debugging from ROS 2/DDS concerns. Nothing about the
  ROS 2/DDS services was broken; this was a deliberate simplification,
  not a rollback from failure. Easy to re-add later.

## Down / parked (not resolved today)

- **Python control script (MAVSDK) — connection not yet confirmed
  receiving data.**
  - `udp://:14540` → rejected, MAVSDK needs an explicit host.
  - `udp://0.0.0.0:14540` → connected but deprecated warning; `udp://`
    is ambiguous about listen-vs-connect direction in current MAVSDK.
  - Fixed to `udpin://0.0.0.0:14540` (explicit "listen" mode, matching
    that PX4's Onboard MAVLink instance sends *to* us on port 14540).
  - Not yet re-tested after this last fix. Also flagged: `mavlink
    status` showed `partner IP: 192.168.1.103` on all four MAVLink
    instances — not `127.0.0.1` — meaning WSL2 may be resolving
    "localhost" traffic onto the real network interface rather than
    true loopback. This is the top suspect if the script still hangs.
    Next diagnostic steps (not yet run):
    ```bash
    hostname -I                          # confirm that IP is WSL2's own
    nc -ul 14540 | xxd | head            # check raw packets arrive at all
    ```
- **QGroundControl from Windows — dead end, parked.**
  - Tried enabling `MAV_i_BROADCAST` params via the `pxh>` console
    (`param set MAV_0_BROADCAST 1`, `param set MAV_1_BROADCAST 1`,
    `param save`) so PX4 would stop restricting MAVLink to loopback.
  - `param save` succeeded and the params persisted, but `mavlink
    status` continued to show `Broadcast enabled: NO` on every
    instance, even after a full container restart.
  - Conclusion: this image starts its four MAVLink UDP streams via
    direct `mavlink start -u ... -r ... ` shell commands in its own
    startup script, not through the numbered `MAV_i_CONFIG` /
    `MAV_i_BROADCAST` parameter system — so the params aren't wired to
    anything active.
  - Real fix, not yet attempted: run `mavlink stop -u 18570` then
    `mavlink start --help` inside the `pxh>` console to get this
    image's actual flag for broadcast or explicit-target-IP, then
    restart that instance with the right flag. Deliberately paused
    here rather than guessing at flags from memory.
  - User decided to deprioritize this in favor of the Python-console
    path for now.
